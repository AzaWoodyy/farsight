# CI checks run as two chains, and each test file in its own global

`scripts/ci/run.py` runs the selected checks in one job, as two chains side by side: `lint` then `test`, and `load` then `typecheck` then `build` then `eval`. Before, the database was loaded in its own step and the seven test passes ran one file after the other: on the runs of 21 November 2026 the load took 29 to 40 s and the tests about 260 s of a job of 265 to 348 s.

## Rules

- The tests never read the loaded rows: each `testDb()` (`scripts/fixtures/test-db.ts`) creates its own schema, with a random name, in the database of `TEST_DATABASE_URL`. They only need the roles of `db/roles.sql` and that database, which the workflow creates in a step of their own. So `load` (`bun run db:load --allow-older-summaries`) runs beside them.
- `typecheck`, `build` and `eval` read the loaded schema: they come after `load` in its chain, and are reported as failed without running when it failed. The type check reads it through `next typegen`, which runs `next.config.ts` and its figures (`HOW_FACTS`): on an empty server it fails with `relation "ingest_runs" does not exist`. It stays before the build, which rewrites the generated route types.
- `bun run test` is `bun test scripts --parallel`: a pool of worker processes, as many as there are cores, each giving every file it runs a fresh JavaScript global and module registry (`--parallel` implies `--isolate`). A file cannot depend on what another left in memory. Files do share the Postgres server, the filesystem and the ports: a test takes a random schema, a temp directory and a port given by the system, never a fixed one.
- `scripts/ci/test.py` runs the suite twice: in the written order, then with `--randomize` and a seed drawn for the run, which shuffles the tests inside each file. It used to replay six fixed seeds after the written order: seven passes, 141 to 150 s of a job of 193 to 197 s, and six orders. A new seed each run tries a new order, and over many runs more of them. What is given up: a later change can break one of the six orders that used to pass, and the one order drawn for its run can miss it, until a later run draws an order that shows it. The price is a failure that can land on a pull request that did not cause it: the last line of the check gives the command that replays the order (`python3 scripts/ci/test.py <seed>`), and a test that fails under an order is fixed, not rerun until it passes.
- Two chains, as there were two workers before: the test workers already take the 4 vCPU of a public runner, and a third chain beside them was not measured.
- The Postgres container gets `--shm-size 1g`. Docker's default is 64 MB of shared memory, which the parallel queries allocate from: a local container that had run the suite many times had 62 MB of it taken and failed 140 tests with `could not resize shared memory segment … No space left on device`. A container of a CI run is new, and did not fail with one test process; the margin is for several.
- Each chain keeps the log of a check in a file and prints it in a group when both chains are done, with its exit status and its duration, so a slow check is visible without downloading the log.
