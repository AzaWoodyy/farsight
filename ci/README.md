# CI data snapshot

`data.json` pins the numerical eval expectations to a frozen snapshot: the raw datasets of `raw.tar.zst`, in git, and the in-game summaries (`ingame.jsonl.zst`) of the GitHub release its `tag` names (currently `data-20261121-4`, the last data release published: schema v12, 31 leagues, the series known only from Leaguepedia's match schedule, each team's logo file, in-game summaries of derive 5). That release is kept for this use and must not be deleted. Both archives are checked with SHA-256, after every cache hit too. Update this descriptor and eval expectations together in a reviewed PR; a new pin needs a release holding the `ingame.jsonl.zst` of a full `data:fetch` (`zstd` of `data/raw/ingame.jsonl`).

`raw.tar.zst` contains the fourteen normalized Cargo/Data Dragon datasets, `schedule.json` (Leaguepedia's match schedule) and `team_logo_files.json` (which team logo files the wiki has, and their exact names) included. They were fetched again from Leaguepedia and Data Dragon a few minutes after that release's own fetch (21 November 2026), by a full `data:fetch` with the release's throttle and the release's in-game summaries in place (no Riot JSON downloaded). The archive is a deterministic USTAR (mode 0644, owner 0, mtime 0, empty owner names, in the order of the descriptor, ended by two zero blocks without record padding) compressed with `zstd -19`; rewriting the previous archive's files that way gives it back byte for byte. Postgres is loaded from the raw datasets. `player_images.json` and `team_logo_files.json` hold Leaguepedia's photo and logo metadata (file names and dates); the images themselves are fair use and are not in the snapshot. The release does not publish them. Rebuilt with the release's in-game summaries, they give a database whose tables match the release row for row, except `ingest_runs` (timestamps and fetch counters). Keeping this compressed fixture in Git makes the ingestion rebuild reproducible without publishing another release or exposing R2 credentials to PRs. Individual dataset hashes are in the descriptor. The extractor accepts only those regular files; the in-game summaries come from the pinned release. Raw Riot JSON is deliberately excluded. In-game derivation definitions are exercised by the V4/V5 synthetic fixtures in the server tests; a change of their calculation must add a real, small Riot corpus and bump `DERIVE_VERSION`. The dragons and souls of derive 3 are tested on `scripts/data/fixtures/dragons.json`, real games cut down to their dragon events. The pinned summaries are derive 5: they hold the dragons and souls, the Leaguepedia fallbacks (damage, vision, rune pages, heralds, patch), the minute statistics only for games that reached the minute, and the credited first blood (tested on `scripts/data/fixtures/first-blood.json`, real games cut down to their first kills and Riot's flags). A later bump that only adds fields keeps `DERIVE_COMPATIBLE` at the pinned version, so the load keeps the pinned summaries without the new columns (`db:load --allow-older-summaries`) until the snapshot is re-pinned; a bump that changes existing numbers raises it and needs summaries recomputed from R2 before the re-pin.

Source data: [Leaguepedia](https://wiki.leagueoflegends.com/en-us/), under [CC BY-SA 3.0](https://creativecommons.org/licenses/by-sa/3.0/), and Riot Games [Data Dragon](https://developer.riotgames.com/docs/lol#data-dragon). The snapshot is a transformed copy of their public esports scoreboards, player and tournament metadata and game summaries. The derived Leaguepedia data is shared under the same CC BY-SA 3.0 license. This license applies to the fixture data; it does not establish a license for the application code.

PRs use the read-only workflow token only for downloading the pinned assets. There are no OpenRouter, R2, Langfuse or Vercel secrets in CI. A fork's PR reads the public release with its own read-only token and sees no secret. Only main writes snapshot caches. No PR cache or artifact is consumed by a privileged deployment.

The stable `PR checks` job always runs, including for documentation edits. Product checks are selected conservatively by `scripts/ci/affected.ts`; unknown paths select every check. PRs compare their full diff against main; main compares the range since the last commit whose main run succeeded under this rule, so a failed or cancelled run is checked again by the next push, and runs every check when no such commit is found. Every check that reads data loads Postgres from the snapshot with the PR's own ingestion code (`db:load`, which first checks the derived rows: orphans, coverage, derivation). Next's own type check remains enabled. Independent commands run on two workers; the separate type check finishes before the build to avoid concurrent generated-type writes.

Make `PR checks` required in the GitHub ruleset for `main`, prohibit direct pushes, and require review of CI changes before publication. These repository settings are separate from the workflow. The Deploy workflow waits for successful CI on main and checks out that exact validated SHA; a manual invocation also requires successful CI for the exact checked-out commit.

The snapshot holds raw data, not a database: a schema change needs no new pin, since `db:load` applies every migration of the PR before it copies the rows.
