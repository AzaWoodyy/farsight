# Farsight

This code base is yours. What it's for and how it's built are your call, and you are going to be the one that keeps building on it.

Natural-language research agent over League of Legends esports data, a portfolio project deployed at `askfarsight.com`. A question ("Chovy's results at every Worlds") goes through four visible steps: understand (entities and aliases such as Chovy / 정지훈 / Jihun), build the query behind a schema guard, execute and self-correct on empty or error, format (sortable table, summary sentence, sources, follow-ups).

## Decisions

These decisions describe the current implementation.

- **Orchestration**: AI SDK 7 alone, with the four steps hand-coded and streamed to the UI as typed data parts. LLM calls go through OpenRouter (`@openrouter/ai-sdk-provider`) on a capped key.
- **Runtime**: Vercel Functions on Node 26 in `fra1`, without `bunVersion`. Bun is the package manager and runs local scripts.
- **Database** (trial branch, `docs/postgres.md`): Postgres (Neon in production) at `DATABASE_URL`, read through the asynchronous `Db` interface (`src/lib/db`) as the read-only role `farsight_app` (`db/roles.sql`); Neon's WebSocket pool for a Neon host, node-postgres elsewhere. Its rows are derived from the raw cache (`scripts/data/derive.ts`) and loaded by `bun run db:load`: every migration into a fresh schema, `COPY`, then a swap (in place when the plan cannot hold two copies). The Data release still builds and publishes the SQLite file from the same rows (`data:build`).
  - Normalized schema (v10): players (with their dated photos), teams (with their Leaguepedia abbreviation), champions, items (with their Data Dragon kind, `src/lib/domain/items.ts`), runes (keystones, minor runes and stat shards, with their tree) and summoner spells stored as integer ids with lookup tables, plus SQL views that put names back for the agent and for text-to-SQL. Keep only the columns, tables and indexes that the `v_*` views and the tools read; the raw cache keeps the rest, so a rebuild can bring a column back.
  - In-game stats are computed at ingestion and stored in SQL (`game_player_stats`, `game_team_stats`, views `v_game_player_stats`, `v_game_team_stats`, `v_ingame_coverage`); definitions live in `scripts/data/ingame.ts`. Dragon kills by element and the dragon soul come from the same timelines (`game_dragons`, view `v_game_dragons`, `game_team_stats.dragon_soul` / `soul` / `elder_dragons`; element keys and labels in `src/lib/domain/dragons.ts`). The minute-by-minute detail never goes to SQL: the raw Riot JSON of each game is one object in Cloudflare R2, read one game at a time through `src/lib/storage` (local filesystem store for tests and the ingestion cache). The `game_timeline` tool reads it at runtime with a read-only R2 token (`R2_READ_*`), behind the Vercel Runtime Cache; definitions in `src/lib/sources/timeline.ts`.
  - Budget: about 570 MB in Postgres, under Neon's free 1 GB. The SQLite release file stays under 190 MB (`data:build` and `data:package` warn from 170 MB, `data:package` refuses more). `bun run size` (end of `bun run build`) measures `/api/ask`, `/api/card`, `/q` and `/en/q` from the Next traces and fails the build above 250 MB or when one ships a SQLite file.
  - Finish every SQLite build with `PRAGMA journal_mode=DELETE; VACUUM;`, because a WAL database can fail to open on a read-only filesystem.
  - Postgres dialect: text is `COLLATE "C"` and flags stay 0/1 integers, as in SQLite; a bare column beside an aggregate is `ANY_VALUE` (or the row of the `MAX`, `ARRAY_AGG(… ORDER BY …)[1]`); an ordering on a nullable column says `NULLS FIRST` / `NULLS LAST`, SQLite's order; `MAX(n, x)` is `atLeast` (NULL stays NULL); `LIKE` is `ILIKE`. Number parameters are typed by the driver adapter.
- **Queries**: typed, parameterized tools for common intents, with guarded text-to-SQL as the fallback. Guarded means a static pass (`src/lib/agent/guard.ts`: a single SELECT, allow-listed tables and columns, no server function, a forced `LIMIT`), then the database itself: generated SQL runs in a `READ ONLY` transaction as `farsight_sql`, which reads only the `v_*` views, under a 4-second `statement_timeout`, with independent row and byte limits cut on the server (`src/lib/db/generated-query.ts`).
- **Hosting**: a separate Vercel project on the Hobby plan, sharing its quotas with the portfolio site. Rate limiting per IP is required.
  - Production is deployed by the `Deploy` workflow (`vercel deploy --prod` from GitHub Actions, build on Vercel): after successful `PR CI` on the current `main` SHA and after each successful `Data release` on `main`. The Vercel Git integration stays off (`git.deploymentEnabled: false`); previews are manual. Details in `docs/deploy.md`.

- **Pages and the database**: a page never opens the database while it renders, with one exception: the two pages a link to an answer opens (`/q`, `/en/q`, see Link previews), which keep the home page's metadata when it cannot be read. A prerendered page is rendered again at request time, in its own function, for the crawlers Next does not stream to (Google's inspection tool, link previews). Figures a page shows, and the sitemap's dates, are read by `next.config.ts` from `DATABASE_URL` when the build starts and inlined (`HOW_FACTS`, `src/app/how/facts.ts`). Check a new page with a `Google-InspectionTool` user agent against a build served without a reachable database.

- **Schema contract**: `src/lib/db/schema.ts` owns the SQLite DDL, `SCHEMA_VERSION` and `PG_MIGRATION`; `db/migrations/NNNN_name.sql` is the same schema in Postgres, applied in order with checksums (`scripts/db/migrations.ts`), and `openDb` refuses a database at another migration. Table/view changes require a new migration and the SQLite DDL together, updating the versioned fingerprint test, and a reload. Index changes preserve the schema version.

- **Languages**: French and English, chosen by the URL alone. French keeps `/` and `/mentions-legales`; English is `/en` and `/en/legal-notice`. Each language has its own root layout (`src/app/(fr)`, `src/app/en`) so `<html lang>` is static, and an unmatched URL gets the bilingual `src/app/global-not-found.tsx` (`experimental.globalNotFound`); no proxy, cookie or `Accept-Language` redirect. Paths and the public list are in `src/app/i18n/locales.ts`, texts in typed catalogs (`en` typed on `fr`): `src/app/i18n/shell.ts` and `ui.ts` for the pages, `src/lib/agent/messages.ts` for what the agent writes. The page sends its language with each question (`locale` in the `/api/ask` body) and the agent answers in it (`withLocale`, French by default, so tests and the eval stay French unless a case sets `locale`). Questions are understood in both languages whatever the page. The tools write their two languages side by side with `say(fr, en)` (the French expression first, untouched); a text read later than it is defined (a label table) is a `phrase(fr, en)` resolved with `tr()`, never a string built at module load. `PUBLIC_LOCALES` decides the switch, hreflang, the sitemap and `noindex`: both languages are public. A new text needs both languages, and a new follow-up question must be one the router understands in its language (the English eval cases, tag `english`).

- **Link previews**: a link to an answer (`/?q=…`, `/en?q=…`) is rewritten (`next.config.ts`) to a page rendered per request (`/q`, `/en/q`), the same home page with the answer in its Open Graph and Twitter metadata: its title, its first sentence and its image (`/api/card`, drawn by `src/app/brand/answer-card.tsx`). The home pages without a question stay static. The card (`src/lib/agent/share.ts`) is computed by the rules alone (`withoutLlm`: a crawler never costs a model call) and outside tracing, from the answer and never from the visitor's text; it exists only when a typed tool answered with rows and no unread word, otherwise the link keeps the site's card. The canonical stays the home page. A function that reads the database must be listed in `next.config.ts` (`CARD_ROUTES`) and in `scripts/size.ts`. The generated images (this card and the site's own, `src/app/brand/share-card.tsx`) are set in Geist Mono like the pages: `src/app/brand/card-font.ts` reads a static TTF kept in the repository (OFL), because next/og reads no WOFF2. Look at a card after changing its layout: a monospaced line is wide, so long names wrap or are cut on purpose.

- **Observability**: Langfuse Cloud (Hobby), one trace per question with one observation per step and one generation per LLM call (AI SDK telemetry callbacks), plus a thumbs up / down score (`/api/feedback`). Off without the three `LANGFUSE_*` variables (local, eval). No IP, cookie or visitor identifier in a trace: only a random conversation id made up by the browser and kept in page memory, sent as the Langfuse session; spans are sent after the response (`after`). Observation names and tags in `src/lib/agent/trace.ts` are what the Langfuse filters target: keep them stable.

## Data

- Source: Leaguepedia Cargo tables (CC BY-SA 3.0). Every answer cites and links its Leaguepedia pages. Data Dragon provides champion, item and rune names and icons, mapped from Leaguepedia display names (for example Wukong is `MonkeyKing`).
- In-game source: the Riot game JSON Leaguepedia hosts (`PostgameJsonMetadata` lists them; pages `V4 data:…` / `V5 data:…` and `…/Timeline`), about 28 000 games of the scope. The LPL has none, and Oracle's Elixir and the lolesports live stats are deliberately not used: an in-game question about the LPL (or any scope where `v_ingame_coverage.ingame_games` is 0) answers that the data is absent for that scope.
- Player identity: a scoreboard link (`ScoreboardPlayers.Link`) is not always the player page; the case drifts (`caPs`) and an older handle stays on old games (`ZionSpartan` for Darshan). `data:fetch` resolves the links through `PlayerRedirects.AllName`, and `data:build` puts every link of a player on one row with `canonical(link)` (`scripts/data/identity.ts`): the exact page, a page at another case, then a redirect name. A name that leads to several pages is not merged, and each raw link stays an alias of its player.
- Anonymous `action=cargoquery` is rate-limited on the first call, so ingestion uses `Special:CargoExport`: one request at a time, ≥ 2 s apart, backoff on errors, every raw response cached on disk. Query by league with `limit=5000` pagination rather than stage by stage.
- Riot JSON goes through the MediaWiki API under the same throttle (shared with Cargo, `maxlag=5`, Retry-After honoured, explicit User-Agent), two games per request. Ingestion is resumable: one gzip object per game in `data/raw/riot` and R2 (when `R2_*` is set, a game missing locally is read from R2, in parallel and outside the wiki budget, before going to the wiki), one summary line per game appended to `data/raw/ingame.jsonl`; a rerun skips what is done. Bump `DERIVE_VERSION` when a definition changes: the next fetch recomputes the summaries from the cached JSON without the network. When the change only adds fields, keep `DERIVE_COMPATIBLE` at the older version: `data:build` keeps those summaries with the new columns NULL (the CI rebuild from the pinned snapshot depends on it), and a release still refuses them.
- Team abbreviations: `data:fetch` saves the Cargo tables `Teams` (page and `Short`) and `TeamRedirects` (older names), and `data:build` gives each scoreboard team the `Short` of its page, or of the page its name redirects to (`teams.short`). `understand` reads them as aliases ("KCB"), derives "KC Blue Stars" from the parent team's abbreviation and the singular "Blue Star", and reads an abbreviation that is an everyday word ("RED") only in capitals; two letters without a digit are never read. Curated shorthands and franchises in `understand.ts` still win over them.
- Player photos: Leaguepedia headshots (Cargo `PlayerImages`) dated by the tournament they were taken for, in `player_images`; the answer shows the photo of the period (`src/lib/domain/player-photos.ts`). They are fair use (Riot Games and the leagues), not CC BY-SA: keep only file names in the database, releases and fixtures, and let the browser load the image from Fandom's CDN. Never copy the images to R2, Blob or a release.
- Team logos and dragon icons: same fair-use rule as the photos (file names only, image loaded from Fandom's CDN, `src/lib/domain/wiki-images.ts`). `src/lib/domain/team-logos.json` maps each team name that played a game to its square logo file on Leaguepedia, with a `tone` for a logo nearly black or nearly white all over (measured on its opaque pixels); the view puts a contrasting plate behind it only on a page of the same tone (`.entity-icon`), so no logo is special-cased. The file is prototype storage, generated once: the durable place is a column of `teams` filled by `data:fetch` / `data:build`, like the photos.
- Rune icons: the database stores what the current Data Dragon lists; removed runes and stat shards fall back to the unversioned `cdn/img/` paths in `src/lib/domain/rune-icons.ts`.
- Display lab (`/lab`, preview and local only): every tool and its variations behind a floating menu, drawn by the production views from real answers computed without the LLM by `bun run lab:build` (part of `bun run build`; skipped when `VERCEL_ENV` is `production`, where the page answers 404). The catalogue is `src/app/lab/catalog.ts`; add a variation there when a tool or a layout gains one.
- Scope is fixed in `src/lib/domain/leagues.ts`. Ingestion, league names, cues and dated historical-family filters derive from it. Explicit historical names retain their own scope.
- Updates: the weekly `Data release` workflow refetches the Cargo tables, restores the previous release's `ingame.jsonl.zst`, downloads only new games' Riot JSON (time-boxed), publishes a `data-YYYYMMDD` release, and keeps the 4 newest. The first full Riot catch-up (8-9 h) runs locally, then `bun run data:sync` uploads it to R2.

## Working rules

- Branches are named `<type>/<subject>`, with type `feat`, `fix`, `chore`, `hotfix` or `improve`. Open pull requests against `main`.
- Commit messages and PR descriptions are written in the author's voice, with no tool attribution or AI trailers.
- Before pushing: lint, typecheck, backend tests in normal and randomized order, deterministic eval (exclude timeline without local JSON/R2), and build must pass, on a Postgres server (`TEST_DATABASE_URL` for the tests, `DATABASE_URL` for the eval and the build; `docs/postgres.md`). `bun run verify` runs them in that order; `.githooks/pre-push` runs it when `core.hooksPath` is set to `.githooks` (opt-in). CI loads a Postgres service container from the verified snapshot in `ci/data.json` (`db:load`); update it and expectations together. Keep its release excluded from retention. Unknown changed paths select every code check. Rebuild only for data inputs, ingestion/shared data dependencies, schema or dependency-lock changes; other PRs keep the verified pinned database. Main uses the pushed range for the same selection. CI runs `data:package --check-only`; full zstd compression stays in Data release.
- PRs target `main`; merge waits for Enzo. A successful CI on `main` triggers production Deploy; never push `main` from a cleanup task.
- The frontend has no automated tests. Verify UI changes by running the app and looking at the changed screen.
- Secrets live in `.env` only, and `.env.example` lists every variable with an empty value.
- The repository is public. Code is MIT (`LICENSE`); the database, data releases and fixtures derived from Leaguepedia stay CC BY-SA 3.0; the Geist Mono file under `src/app/brand/fonts` is OFL 1.1. Commits, PR text, docs and screenshots are readable by anyone: no account id, dashboard URL or personal data in them.

## Audit follow-up

When extending tools, update the registry in `src/lib/agent/tools.ts`; its names, calls, binding and SDK tools derive from that registry. Keep metric routing vocabulary and per-metric derivation definitions aligned. For unresolved audit proposals and verification limits, read `docs/audits/cleanup.md`. Feedback requires `FEEDBACK_SECRET`; without it, feedback controls stay disabled. Rate limits in code are per instance, so retain the shared Vercel firewall rules.
