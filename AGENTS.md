# Farsight

This code base is yours. What it's for and how it's built are your call, and you are going to be the one that keeps building on it.

Natural-language research agent over League of Legends esports data, a portfolio project deployed at `askfarsight.com`. A question ("Chovy's results at every Worlds") goes through four visible steps: understand (entities and aliases such as Chovy / 정지훈 / Jihun), build the query behind a schema guard, execute and self-correct on empty or error, format (sortable table, summary sentence, sources, follow-ups).

## Decisions

These decisions describe the current implementation.

- **Orchestration**: AI SDK 7 alone, with the four steps hand-coded and streamed to the UI as typed data parts. LLM calls go through OpenRouter (`@openrouter/ai-sdk-provider`) on a capped key. The conversation (`/chat`) is a second surface beside this pipeline, which it calls as a tool (Conversation, below).
- **Runtime**: Vercel Functions on Node 26 in `fra1`, without `bunVersion`. Bun is the package manager and runs local scripts.
- **Database** (`docs/postgres.md`): Postgres at `DATABASE_URL` (Neon in production: Postgres 18 in Frankfurt, Launch plan, compute always on, 0.25–2 CU), read through the asynchronous `Db` interface (`src/lib/db`) as the read-only role `farsight_app` (`db/roles.sql`); node-postgres over TCP everywhere (on Vercel Fluid compute with `attachDatabasePool` and Neon's pooled host); Neon's WebSocket driver only with `DATABASE_DRIVER=neon`. Its rows are derived from the raw cache (`scripts/data/derive.ts`) and loaded by `bun run db:load`: every migration into a fresh schema, `COPY`, then a swap (in place when the plan cannot hold two copies). There is no SQLite file and no data release: Postgres and R2 hold the data. What accounts write (saved conversations, daily usage) is in a schema of its own, `farsight_users`, that the load never touches (Conversation, below).
  - Normalized schema (v12, Postgres migration 3): players (with their dated photos), teams (with their Leaguepedia abbreviation and logo file), champions, items (with their Data Dragon kind, `src/lib/domain/items.ts`), runes (keystones, minor runes and stat shards, with their tree) and summoner spells stored as integer ids with lookup tables, plus SQL views that put names back for the agent and for text-to-SQL. Keep only the columns, tables and indexes that the `v_*` views and the tools read; the raw cache keeps the rest, so a rebuild can bring a column back.
  - In-game stats are computed at ingestion and stored in SQL (`game_player_stats`, `game_team_stats`, views `v_game_player_stats`, `v_game_team_stats`, `v_ingame_coverage`); the code is `scripts/data/ingame.ts`, the definitions `docs/adr/0008-ingame-stat-definitions.md`. Dragon kills by element and the dragon soul come from the same timelines (`game_dragons`, view `v_game_dragons`, `game_team_stats.dragon_soul` / `soul` / `elder_dragons`; element keys and labels in `src/lib/domain/dragons.ts`). The minute-by-minute detail never goes to SQL: the raw Riot JSON of each game is one object in Cloudflare R2, read one game at a time through `src/lib/storage` (local filesystem store for tests and the ingestion cache). The `game_timeline` tool reads it at runtime with a read-only R2 token (`R2_READ_*`), behind the Vercel Runtime Cache; code in `src/lib/sources/timeline.ts`, definitions in `docs/adr/0010-timeline-definitions.md`.
  - Budget: about 575 MB in Postgres; a swap holds two copies for the time of a load. `bun run size` (end of `bun run build`) measures `/api/ask`, `/api/chat`, `/api/card`, `/q` and `/en/q` from the Next traces and fails the build above 250 MB or when one ships a SQLite file.
  - Postgres dialect: text is `COLLATE "C"` and flags stay 0/1 integers, as in SQLite; a bare column beside an aggregate is `ANY_VALUE` (or the row of the `MAX`, `ARRAY_AGG(… ORDER BY …)[1]`); an ordering on a nullable column says `NULLS FIRST` / `NULLS LAST`, SQLite's order; `MAX(n, x)` is `atLeast` (NULL stays NULL); `LIKE` is `ILIKE`. Number parameters are typed by the driver adapter.
- **Queries**: typed, parameterized tools for common intents, with guarded text-to-SQL as the fallback. Guarded means a static pass (`src/lib/agent/guard.ts`: a single SELECT, allow-listed tables and columns, no server function, a forced `LIMIT`), then the database itself: generated SQL runs in a `READ ONLY` transaction as `farsight_sql`, which reads only the `v_*` views, under a 4-second `statement_timeout`, with independent row and byte limits cut on the server (`src/lib/db/generated-query.ts`).
- **Hosting**: a separate Vercel project on the Hobby plan, sharing its quotas with the portfolio site. Rate limiting per IP is required.
  - Production is deployed by the `Deploy` workflow (`vercel deploy --prod` from GitHub Actions, build on Vercel): after successful `PR CI` on the current `main` SHA, and on demand. Data updates need no deployment. The Vercel Git integration stays off (`git.deploymentEnabled: false`); previews are manual. Details in `docs/deploy.md`.

- **Pages and the database**: a page never opens the database while it renders, with one exception: the two pages a link to an answer opens (`/q`, `/en/q`, see Link previews), which keep the home page's metadata when it cannot be read. A prerendered page is rendered again at request time, in its own function, for the crawlers Next does not stream to (Google's inspection tool, link previews). Figures a page shows, and the sitemap's dates, are read by `next.config.ts` from `DATABASE_URL` when the build starts and inlined (`HOW_FACTS`, `src/app/how/facts.ts`). The home page's answers are inlined the same way (`HOME_PROOFS`, `src/app/home-proofs-data.ts`): `next.config.ts` runs `scripts/home/proofs.ts`, which asks five fixed questions in each language by the rules alone and keeps what each view shows; a question that no longer gives its view is left out with a warning, and without `DATABASE_URL` the page shows none. One is shown at random per load (`?proof=0`…`4` pins one), chosen by an inline script before the first paint so the page stays static. `bun run pages:check` (in `verify` and CI, after the build) serves the build without a database and requests every page as `Google-InspectionTool` and as a browser: each must answer 200.

- **Conversation** (`/chat`, `/en/chat`; ADRs 0117 to 0125): a signed-in, invited account talks with the data over several turns instead of asking one question at a time. It is a second surface, with its own page, routes and agent loop; the four-step pipeline and the question page are unchanged.
  - Agent (`src/lib/agent/chat.ts`): one AI SDK tool loop with four tools: `ask_data` (a standalone question handed to the pipeline), `league_paths` (paths of teams between leagues, computed by the code for the LEC and the LCK), `run_sql` (the model's own query, behind the SQL guard and `farsight_sql`) and `render_html` (a composed view). The model checks each `ask_data` result against the question and says a datum is absent only after a query of its own came back empty. A turn shows one query result; an exploratory query is not shown. It needs the model: without it the route answers 503.
  - History: the server keeps nothing between turns. The browser sends the messages back, and earlier results reach the model as real tool calls rebuilt from them, never as text.
  - Display: result cards are built on the server (`src/lib/agent/chat-card.ts`) and are not the answer views of the question page. A view composed by the agent is drawn in an `iframe` with `sandbox="allow-same-origin"` and no `allow-scripts`, which receives the page's stylesheets; the model writes with the `kit-*` classes (`src/app/chat/chat.css`) and the site's colour variables only. Never add `allow-scripts` to that frame.
  - Accounts: Clerk is loaded on `/chat`, `/en/chat` and their API routes only. `src/proxy.ts` matches those paths alone and lets the request through when the conversation is not configured. The conversation is open when `CLERK_SECRET_KEY`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` and `THREADS_DATABASE_URL` are all set (`chatConfigured`, `src/lib/auth/chat-config.ts`) and says it is closed otherwise, whatever the environment: the site builds and answers without any Clerk key (CI). A new page or route of the conversation checks `chatConfigured()` first.
  - Access is by invitation: an account talks to the agent only when its Clerk public metadata holds `{"chat": true}`, read in the session token first, then through Clerk's API with a short memory (`src/lib/auth/chat-access.ts`). Every API route of the conversation runs that check.
  - Threads and usage (`src/lib/threads/store.ts`, `db/threads.sql`): schema `farsight_users`, role `farsight_threads`, connection string `THREADS_DATABASE_URL`. `db:load` swaps `farsight` and never touches that schema; `farsight_app` stays read-only. 30 conversations per account, kept until their owner deletes them (a 31st pushes the oldest out), and 100 messages per account and UTC day. A deleted account takes its conversations with it (Clerk webhook `user.deleted`, `/api/clerk/webhook`, signed with `CLERK_WEBHOOK_SIGNING_SECRET`). A row holds Clerk's user id and no other personal data.
  - Security headers: the two conversation pages get a wider Content-Security-Policy for Clerk, whose host is read from the publishable key (`next.config.ts`); the rest of the site keeps its policy.
  - Test data: `?data=worst|empty|one|long` replaces the saved conversations on the conversation page in development only (`src/app/chat/worst-case.ts`); look at it after changing the conversation's layout.
  - Setup of the Clerk instance, the webhook, the session token and the schema is in `docs/deploy.md`.

- **Schema contract**: `src/lib/db/schema.ts` owns the DDL the derivation takes its tables and columns from (written in SQLite's dialect, checked in memory by the tests), `SCHEMA_VERSION`, `PG_MIGRATION` and `PG_MIGRATION_READ` (the oldest migration the code reads, lower than the newest only when the code tolerates what the newest adds being absent); `db/migrations/NNNN_name.sql` is the same schema in Postgres, applied in order with checksums (`scripts/db/migrations.ts`), and `openDb` refuses a database older than `PG_MIGRATION_READ` and accepts a newer one, so a migration only adds and the load lands before the deploy (`docs/postgres.md`). Table/view changes require a new migration and that DDL together, updating the versioned fingerprint test, and a reload. Index changes preserve the schema version.

- **Languages**: French and English, chosen by the URL alone. French keeps `/` and `/mentions-legales`; English is `/en` and `/en/legal-notice`. Each language has its own root layout (`src/app/(fr)`, `src/app/en`) so `<html lang>` is static, and an unmatched URL gets the bilingual `src/app/global-not-found.tsx` (`experimental.globalNotFound`); no proxy, cookie or `Accept-Language` redirect decides the language. The only proxy and the only cookies of the site are Clerk's, on the conversation paths (Conversation, below). Paths and the public list are in `src/app/i18n/locales.ts`, texts in typed catalogs (`en` typed on `fr`): `src/app/i18n/shell.ts` and `ui.ts` for the pages, `src/app/i18n/chat.ts` for the conversation page, `src/lib/agent/messages.ts` for what the agent writes. The page sends its language with each question (`locale` in the `/api/ask` body) and the agent answers in it (`withLocale`, French by default, so tests and the eval stay French unless a case sets `locale`). Questions are understood in both languages whatever the page. The tools write their two languages side by side with `say(fr, en)` (the French expression first, untouched); a text read later than it is defined (a label table) is a `phrase(fr, en)` resolved with `tr()`, never a string built at module load. `PUBLIC_LOCALES` decides the switch, hreflang, the sitemap and `noindex`: both languages are public. A new text needs both languages, and a new follow-up question must be one the router understands in its language (the English eval cases, tag `english`).

- **Link previews**: a link to an answer (`/?q=…`, `/en?q=…`) is rewritten (`next.config.ts`) to a page rendered per request (`/q`, `/en/q`), the same home page with the answer in its Open Graph and Twitter metadata: its title, its first sentence and its image (`/api/card`, drawn by `src/app/brand/answer-card.tsx`). The home pages without a question stay static. The card (`src/lib/agent/share.ts`) is computed by the rules alone (`withoutLlm`: a crawler never costs a model call) and outside tracing, from the answer and never from the visitor's text; it exists only when a typed tool answered with rows, no unread word and no uncertain pick among homonyms, otherwise the link keeps the site's card. The canonical stays the home page. A function that reads the database must be listed in `outputFileTracingExcludes` of `next.config.ts` (through `CARD_ROUTES` for the routes of a link) and in `scripts/size.ts`. The generated images (this card and the site's own, `src/app/brand/share-card.tsx`) are set in Geist Mono like the pages: `src/app/brand/card-font.ts` reads a static TTF kept in the repository (OFL), because next/og reads no WOFF2. Look at a card after changing its layout: a monospaced line is wide, so long names wrap or are cut on purpose.

- **Observability**: Langfuse Cloud (Hobby), one trace per question with one observation per step and one generation per LLM call (AI SDK telemetry callbacks), plus a thumbs up / down score (`/api/feedback`). Off without the three `LANGFUSE_*` variables (local, eval). No IP, cookie or visitor identifier in a trace: only a random conversation id made up by the browser, sent as the Langfuse session; spans are sent after the response (`after`). On the home page that id is kept in page memory. A turn of the conversation (`/chat`) is a trace of the same shape tagged `surface:chat`, and its session is the id its conversation is saved under, so it lasts as long as the conversation; no account id, e-mail address or name is sent. Observation names and tags in `src/lib/agent/trace.ts` are what the Langfuse filters target: keep them stable. `bun run eval:candidates` (`docs/eval-candidates.md`) reads them back to propose eval cases: its report stays outside the repository (`~/.farsight/eval-candidates/`), and no visitor question, trace id or session id ever goes into a commit, PR or comment; Enzo alone turns a candidate into a case.

## Data

- Source: Leaguepedia Cargo tables (CC BY-SA 3.0). Every answer cites and links its Leaguepedia pages. Data Dragon provides champion, item and rune names and icons, mapped from Leaguepedia display names (for example Wukong is `MonkeyKing`).
- In-game source: the Riot game JSON Leaguepedia hosts (`PostgameJsonMetadata` lists them; pages `V4 data:…` / `V5 data:…` and `…/Timeline`), about 28 000 games of the scope. The LPL has none, and Oracle's Elixir and the lolesports live stats are deliberately not used: an in-game question about the LPL (or any scope where `v_ingame_coverage.ingame_games` is 0) answers that the data is absent for that scope.
- Player identity: a scoreboard link (`ScoreboardPlayers.Link`) is not always the player page; the case drifts (`caPs`) and an older handle stays on old games (`ZionSpartan` for Darshan). `data:fetch` resolves the links through `PlayerRedirects.AllName`, and the derivation puts every link of a player on one row with `canonical(link)` (`scripts/data/identity.ts`): the exact page, a page at another case, then a redirect name. A name that leads to several pages is not merged, and each raw link stays an alias of its player.
- Anonymous `action=cargoquery` is rate-limited on the first call, so ingestion uses `Special:CargoExport`: one request at a time, ≥ 2 s apart, backoff on errors, every raw response cached on disk. Query by league with `limit=5000` pagination rather than stage by stage.
- Riot JSON goes through the MediaWiki API under the same throttle (shared with Cargo, `maxlag=5`, Retry-After honoured, explicit User-Agent), two games per request. Ingestion is resumable: one gzip object per game in `data/raw/riot` and R2 (when `R2_*` is set, a game missing locally is read from R2, in parallel and outside the wiki budget, before going to the wiki), one summary line per game appended to `data/raw/ingame.jsonl`; a rerun skips what is done. With R2, the summaries are also one object (`derived/ingame.jsonl.zst`): `data:fetch` takes from it the lines the local file lacks before the games, and writes the whole file back after them, so a run on an empty machine recomputes nothing. Two summaries can share a game (a game and its remake, two Riot games filed under one scoreboard): the derivation tries them by most champions of the scoreboard, then the scoreboard's game length, then longer game, then smaller key (`summaryRank`), and keeps the first it can map to the scoreboard's players, whatever the order of the file (`bestFirst`, `scripts/data/derive.ts`). Bump `DERIVE_VERSION` when a definition changes: the next fetch recomputes the summaries from the cached JSON without the network. When the change only adds fields, keep `DERIVE_COMPATIBLE` at the older version: the derivation keeps those summaries with the new columns NULL, and `db:load` refuses them without `--allow-older-summaries` (CI passes it: its pinned summaries cannot be recomputed). `db:load` writes nothing when the derived rows fail a check of `scripts/data/checks.ts` (a row without its parent, a league of the scope without a game, a file `data:fetch` did not save, `ingame.jsonl` included), unless `--allow-incomplete` is passed.
- Franchises: a team that changed name is one team when `FRANCHISES` (`src/lib/agent/understand.ts`, kept by hand) lists its names; Kameto Corp (the 2020 season) and Karmine Corp are one.
- Team abbreviations: `data:fetch` saves the Cargo tables `Teams` (page and `Short`) and `TeamRedirects` (older names), and the derivation gives each scoreboard team the `Short` of its page, or of the page its name redirects to (`teams.short`). `understand` reads them as aliases ("KCB"), derives "KC Blue Stars" from the parent team's abbreviation and the singular "Blue Star", and reads an abbreviation that is an everyday word ("RED") only in capitals; two letters without a digit are never read. An abbreviation two teams share (NIP) names the only one of them that played in the competition and period of the question, otherwise the one with more games. Curated shorthands and franchises in `understand.ts` still win over them.
- Series without a scoreboard: `data:fetch` saves the whole `MatchSchedule` of the scope (`schedule.json`), and the derivation (`scripts/data/derive.ts`) keeps in `series_results` (view `v_series_results`, migration 2) the decided matches no scoreboard game covers (`scripts/data/schedule.ts`): teams, score, winner, forfeit, date, tab, and no game statistic. The team history, head-to-head and series tools count them with the scoreboards' series and say so in a note (a forfeit is a series, never games); qualifiers stay excluded like the games. A team known only from them is read by its full name alone.
- Player photos: Leaguepedia headshots (Cargo `PlayerImages`) dated by the tournament they were taken for, in `player_images`; the answer shows the photo of the period (`src/lib/domain/player-photos.ts`). They are fair use (Riot Games and the leagues), not CC BY-SA: keep only file names in the database, releases and fixtures, and let the browser load the image from Fandom's CDN. Never copy the images to R2, Blob or a release.
- Team logos and dragon icons: same fair-use rule as the photos (file names only, image loaded from Fandom's CDN, `src/lib/domain/wiki-images.ts`). `teams.logo` holds each team's square logo file on Leaguepedia (`scripts/data/team-logos.ts`): `<name>logo square.png`, else its page's, never `Teams.Image`. `data:fetch` checks which exist through the MediaWiki API (50 titles per request, shared throttle, uncached, about 40 requests per run) and stores the exact name the API returns, the one the CDN path is built from. A displayed name that two teams answer to ("Nova Esports", or "Awesome" beside "Awesome (Awesome Spear Academy)") gets no logo. The `tone` of a logo nearly black or nearly white all over is a hand-kept list by file (`src/lib/domain/team-logo-tones.json`), never measured at ingestion; the view puts a contrasting plate behind it only on a page of the same tone (`.entity-icon`), so no logo is special-cased. A release without any logo is refused.
- Rune icons: the database stores what the current Data Dragon lists; removed runes and stat shards fall back to the unversioned `cdn/img/` paths in `src/lib/domain/rune-icons.ts`.
- Display lab (`/lab`, preview and local only): every tool and its variations behind a floating menu, drawn by the production views from real answers computed without the LLM by `bun run lab:build` (part of `bun run build`; skipped when `VERCEL_ENV` is `production`, where the page answers 404). The catalogue is `src/app/lab/catalog.ts`; add a variation there when a tool or a layout gains one.
- Scope is fixed in `src/lib/domain/leagues.ts`. Ingestion, league names, cues and dated historical-family filters derive from it. Explicit historical names retain their own scope.
- Updates: the daily `Postgres update` workflow refetches the Cargo tables, takes the in-game summaries of the previous run from R2, downloads only new games' Riot JSON (R2 first, then the wiki, time-boxed), writes the summaries back to R2 and loads Neon (`db:load`: checks, then swapped in); the app reads it within 5 minutes (its caches). Nothing else publishes data: the weekly `Data release`, `data:build`, `data:package` and `data:pull` are gone. The first full Riot catch-up (8-9 h) runs locally, then `bun run data:sync` uploads it to R2.

## Working rules

- Branches are named `<type>/<subject>`, with type `feat`, `fix`, `chore`, `hotfix` or `improve`. Open pull requests against `main`.
- Commit messages and PR descriptions are written in the author's voice, with no tool attribution or AI trailers.
- The code carries no comments (`farsight/no-comments`, `tools/oxlint/farsight`): names say what the code does, and a non-obvious decision is recorded in `docs/adr` (index in `docs/adr/README.md`; read the area's records before changing its code). Only the comments tools read stay (`oxlint-disable`, `SAFETY:`, `@ts-`, `turbopackIgnore`). `comment-baseline.json` lists the counts still granted per file and only goes down; `/delete-comment` repeats the audit.
- Before pushing: lint, typecheck, backend tests in normal and randomized order, deterministic eval (exclude timeline without local JSON/R2), and build must pass, on a Postgres server (`TEST_DATABASE_URL` for the tests, `DATABASE_URL` for the eval and the build; `docs/postgres.md`). `bun run verify` runs them in that order; `.githooks/pre-push` runs it when `core.hooksPath` is set to `.githooks` (opt-in). CI loads a Postgres service container from the verified snapshot in `ci/data.json` (`db:load`): the raw datasets of `ci/raw.tar.zst` and the `ingame.jsonl.zst` of the GitHub release it names, kept for that use and never to be deleted; update it and expectations together. Unknown changed paths select every check. Main uses the pushed range for the same selection.
- PRs target `main`; merge waits for Enzo. A successful CI on `main` triggers production Deploy; never push `main` from a cleanup task.
- The frontend has no automated tests. Verify UI changes by running the app and looking at the changed screen.
- Secrets live in `.env` only, and `.env.example` lists every variable with an empty value.
- The repository is public. Code is MIT (`LICENSE`); the database, data releases and fixtures derived from Leaguepedia stay CC BY-SA 3.0; the Geist Mono file under `src/app/brand/fonts` is OFL 1.1. Commits, PR text, docs and screenshots are readable by anyone: no account id, dashboard URL or personal data in them.

## Audit follow-up

When extending tools, update the registry in `src/lib/agent/tools.ts`; its names, calls, binding and SDK tools derive from that registry. Keep metric routing vocabulary and per-metric derivation definitions aligned. For unresolved audit proposals and verification limits, read `docs/audits/cleanup.md`. Feedback requires `FEEDBACK_SECRET`; without it, feedback controls stay disabled. Rate limits in code are per instance, so retain the shared Vercel firewall rules. The conversation is bounded by account in the database (the daily message limit), not by a firewall rule.
